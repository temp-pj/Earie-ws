# Go 서버 랜덤 매칭 요구사항과 후속 앱 동작

상태: 서버 실행 범위 v1.1, wire 계약 v1.
이번 구현은 Go 서버만이다. 아래의 iOS 화면·알럿·버튼 동작은 미래 클라이언트 기대 동작을 보존한 것이며 이번 서버 이슈의 구현/완료 조건이 아니다. 서버는 그 동작에 필요한 응답과 상태 정리만 보장한다. iOS 파일·Xcode·실기기 검증은 제외한다.

## 범위

REQ-SCOPE-01: Go 서버의 WebSocket을 확장한다. 별도 REST API/Swift 서버는 만들지 않는다.
REQ-SCOPE-02: 후속 iOS는 랜덤 매칭만 제공할 예정이다. 이번에는 해당 UI를 구현하지 않는다. ID 입력, 직접 방 생성, 친구 초대, 가수 모드, 자동 시작/카운트다운, 재접속 복구, 같은 방 재시작은 제외한다.
REQ-SCOPE-03: 기존 게임 판정·페널티·곡당 시간은 재설계하지 않는다. 10곡 고정, 인원 부족 종료, 결과 후 복귀는 이번 변경에 포함한다.

## 조건 선택

REQ-CAT-01: 연도(10년 단위), 구성(솔로/그룹), 성별(남/여), 음악 분류에서 각각 한 값 또는 상관없음을 선택한다. 연도에는 모든 연대도 제공한다. 다른 항목의 UI에는 명시적 전체 선택을 제공하지 않는다.
REQ-CAT-02: 국가는 UI에서 제거한다. 음악 분류는 한국 유저 기대에 맞춘다. 발라드는 한국 발라드이며 국가 UI 제거를 해외곡 포함으로 해석하지 않는다. 실제 분류 목록은 버전된 카탈로그 데이터로 제공하며 T10에서 출고 전 검수한다.
REQ-CAT-03: 같은 명시 값끼리는 일치, 한쪽 무관이면 상대 값 수용, 양쪽 무관이면 전체 범위, 서로 다른 명시 값은 불일치다. 모든 항목이 호환되어야 한다.
REQ-CAT-04: 모든 연대와 2010년대는 불일치다. 모든 연대는 전체 범위에서 무작위 출제하며 시대별 균등/최소 비율을 보장하지 않는다.
REQ-CAT-05: 방 조건은 생성 시 확정하고 변경하지 않는다. 추가 참가자는 각 항목이 방 조건과 같거나 상관없음이어야 한다. 전체 범위 방에 특정 값만 원하는 요청은 배정하지 않는다.
REQ-CAT-06: 출제 곡이 부족한 조합은 선택할 수 없게 한다. 개별 항목이 아니라 결합 조건을 검증한다. 서버도 검증한다. 제공 가능한 조합은 10곡 출제를 지원해야 한다.

## 매칭과 우선순위

REQ-MATCH-01: 적합하고 빈자리 있는 대기 방을 우선한다. 여러 방이면 서버 생성 순서가 빠른 방을 선택한다.
REQ-MATCH-02: 적합한 방이 없으면 호환 대기자 중 서버 접수 순서가 빠른 사람과 두 명의 새 방을 만든다. 상대가 없으면 방을 만들지 않고 대기한다.
REQ-MATCH-03: 무기한 대기하며 조건을 자동 완화하지 않는다. 등록 거절로 재탐색해도 원래 접수 순서를 유지한다.
REQ-MATCH-04: 사용자당 활성 요청 하나, 요청당 등록 시도 하나만 허용한다. 중복 전달은 순서를 새로 부여하거나 이중 배정하지 않는다.

## 방 및 게임

REQ-ROOM-01: 최대 8명. 최초 둘 중 먼저 요청한 사람이 방장. 추가 입장으로 방장을 바꾸지 않는다.
REQ-ROOM-02: 2명 이상일 때 방장만 수동 시작한다. 시작된 방/결과 방에는 배정하지 않는다.
REQ-ROOM-03: 대기 중 방장 퇴장 시 남은 사람 중 요청 접수 순서가 빠른 사람에게 승계. 한 명이면 방 유지·충원·시작 불가, 0명이면 삭제한다.
REQ-ROOM-04: 게임 중 2명 이상이면 계속 진행하고 방장 승계는 동일하다. 1명이면 조기 종료하고 '상대가 모두 퇴장했습니다' 안내. 0명이면 작업과 방을 정리한다. 진행 중 충원하지 않는다.
REQ-ROOM-05: 한 게임 10곡. 정상 종료 후 결과를 보여주고 각자 로비로 나간다. 동일 방 재시작은 없다.
REQ-ROOM-06: 서버에서 시작 확정 전 등록 완료한 사용자만 게임에 포함한다. 시작이 먼저면 해당 방에 넣지 않고 매칭을 계속한다. 실패 알럿을 보내지 않는다.

## 취소·실패·연결

REQ-CANCEL-01: 취소 즉시 iOS는 로비로 이동한다. 대기열 또는 배정된 참가 상태는 서버가 정리한다. 퇴장/오류 알럿은 없다.
REQ-CANCEL-02: 취소한 요청의 늦은 성공으로 방 화면에 이동하지 않는다. 진행 중 등록이 있으면 취소 기록을 유지하고 성공 결과가 도착하면 정리한다.
REQ-CANCEL-03: 취소 직후 새 requestID로 요청 가능하며 새 접수 순서를 받는다. 이전 요청의 응답·정리는 새 요청에 영향을 주지 않는다.
REQ-CONN-01: 매칭 버튼 시 기존 연결을 재사용하거나 새 연결을 맺는다. 연결만으로 방을 생성/입장하지 않는다. 취소·퇴장만을 이유로 연결을 닫지 않는다.
REQ-CONN-02: 연결 실패 시 알럿 후 로비로 이동한다. 서버 감지 후 대기/방 상태를 정리한다. 기존 방 복구 없이 다음 매칭 때 새 연결을 사용한다.
REQ-CONN-03: 현재 요청의 MATCH_FAILED만 알럿 후 로비 이동한다. 취소/오래된 요청의 오류는 무시한다. 방 만석/시작/종료 경합은 서버 내부 재탐색이다.
REQ-CONN-04: 입장 후 LEAVE_ROOM의 ROOM_LEFT 확인으로 로비 복귀하고 연결은 유지한다. 중복·오래된 퇴장 요청으로 다른 방 상태를 변경하지 않는다.

## 완료 시나리오

| 검증 | 요구사항 | 기대 결과 |
|---|---|---|
| 혼자/호환 두 명/불일치 두 명 | MATCH-01~03, CAT-03~04 | 대기/새 방/각자 대기 |
| 기존 방 여러 개 및 대기자 여러 명 | MATCH-01~03 | 기존 방과 각 서버 순서 우선 |
| 최초 쌍 등록 실패/취소 | CANCEL-01~03 | 유령 등록 없음, 유효 요청 순서 보존 |
| 8번째 자리 동시 입장·게임 시작 경합 | ROOM-01,06 | 정원 보장, 시작 전 등록만 참가 |
| 연타·중복 메시지 | MATCH-04 | 하나의 활성 요청과 참가 등록 |
| 등록 중 취소 및 즉시 재요청 | CANCEL-01~03 | 늦은 결과가 새 요청/화면에 영향 없음 |
| 방장/일반 유저 퇴장 | ROOM-03~04 | 접수 순서 승계 및 인원별 처리 |
| 연결 실패·직접 취소 | CONN-02~03, CANCEL-01 | 실패만 알럿, 서버 정리 |
| 결과 후 퇴장·재매칭 | ROOM-05, CONN-01,04 | 10곡 종료, 연결 재사용, 새 매칭 |

이번 완료 검증은 Go actor 단위 테스트와 실제 WebSocket 테스트 클라이언트로 수행한다. UI 전환/알럿 조건은 서버 응답·오류 구분·상태 정리로 대체 검증하고 UI 구현 여부를 통과로 표시하지 않는다. 2~9개 socket client로 신규/충원/정원/취소/실패를 재현한다. synthetic MusicProvider와 clock으로 10곡 진행 및 조기 종료를 검증한다. 실제 음원 재생과 iOS 연동은 미검증으로 명시한다. 자세한 서버 완료 기준은 tasks.md T9를 따른다.

## 구현을 위한 명확화

REQ-DATA-01: 서버 카탈로그와 향후 iOS 번들의 카탈로그는 같은 버전을 사용한다. 이번에는 서버 loader/validation과 테스트 카탈로그만 필수이며 iOS 번들 반영은 하지 않는다. 가능한 전체 조합 목록을 기준으로 UI가 불가능한 조합을 비활성화한다. 데이터가 없거나 검증되지 않은 카탈로그로 실제 매칭을 제공하지 않는다.
REQ-DATA-02: 양쪽의 조건은 개별적으로 유효해도 교집합에 곡이 부족할 수 있다. 신규 쌍의 확정 조건 역시 출제 가능해야 매칭한다. 상대 선택에 따라 무관을 해소할 때 실제 출제 가능 범위를 벗어나지 않는다.
REQ-GAME-01: 기존 기본 제한 시간 30초를 서버 설정으로 유지한다. 이번에 시간 선택 UI를 추가하지 않는다. START_GAME은 클라이언트의 카테고리/곡 수/시간을 받지 않고 서버가 확정 방 조건·10곡·기존 기본 시간을 사용한다.
REQ-GAME-02: 같은 ISRC의 중복 행은 한 곡으로 계산하고 한 게임에 반복 출제하지 않는다. 리메이크/다른 녹음의 제목 유사성까지 판정하는 새 규칙은 추가하지 않는다.
REQ-FAIL-01: 사용자 부족 외 내부 오류에 의한 게임 중단은 GAME_ABORTED/INTERNAL_ERROR로 구분한다. 조기 종료는 result 상태로 이동하며 점수·승자를 새로 계산하지 않고 안내 후 로비로 나갈 수 있다.

## 이번 서버 검증에서 책임의 구분

| 요구사항 표현 | 서버의 이번 완료 기준 | 후속 iOS 작업 |
|---|---|---|
| 취소 즉시 로비/무알럿 | 요청 scoped 정리, MATCH_CANCELLED, 잘못된 MATCH_FAILED 없음 | 화면 복귀·알럿 억제 |
| 오래된 응답 무시 | 모든 응답 requestID/roomID 정확, 이전 정리가 새 상태에 영향 없음 | 응답 필터링 |
| 연결 실패 알럿 | 연결 종료 감지·대기/Room 정리 | 실패 안내·로비 이동 |
| 선택 불가능한 조합 | allowedRequests/pool 검증, INVALID_CRITERIA | 선택지 비활성화 |
| 결과 후 복귀 | GAME_OVER/GAME_ABORTED, LEAVE_ROOM/ROOM_LEFT, 연결 재사용 | 결과 화면·버튼 |

T9 통과는 서버 독립 구현 완료다. 실데이터 T10과 iOS 연동이 없는 상태에서는 서비스 전체 출시 완료가 아니다.
